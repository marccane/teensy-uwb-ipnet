# uwbnet protocols

## USB

The board enumerates as one composite device with two CDC-ACM ports.
Manufacturer string `uwbnet`, product `UWB-Net`, serial number = the Teensy's
own (unique per board). Teensy VID `16c0`; the PID is the Teensyduino
"Dual Serial" one.

| Interface | Linux node (typical) | Use |
|---|---|---|
| 0 (first CDC) | `/dev/ttyACM0` | framed packet port for the host daemon |
| 2 (second CDC) | `/dev/ttyACM1` | text console for humans |

Baud rate and line settings are ignored. The device sends nothing on a port
whose DTR is low, so open the port (which raises DTR) before expecting data.

### Packet port framing

Every message is `COBS(type, payload...)` followed by one `0x00` byte.
COBS ([Cheshire & Baker](https://en.wikipedia.org/wiki/Consistent_Overhead_Byte_Stuffing))
removes all zero bytes, so `0x00` only ever appears as the delimiter. A reader
resynchronises by discarding bytes up to the next `0x00`.

| Type | Direction | Payload |
|---|---|---|
| `0x01` DATA | both | exactly one IPv4 or IPv6 packet, 1..1011 bytes |
| `0x02` CMD | host → device | one console command line, ASCII, no terminator, max 255 bytes |
| `0x03` RESP | device → host | the command's output, ASCII with `\r\n` line ends, max 2048 bytes |

- The maximum IP packet (MTU) is **1011 bytes**. Larger DATA payloads are
  dropped and counted as `usb ... bad`.
- The device resets its decoder whenever the port is opened (DTR rises). The
  host should still send a single `0x00` first, to end any partial message
  left in the pipe.
- Every CMD gets exactly one RESP, in order. DATA messages may arrive between
  a CMD and its RESP. While the port is open a RESP is never dropped: the
  device stops reading until the host has made room for it.
- Flow control is USB's own: once `ipqueue` IP packets (default 8, at most
  16) are waiting for the radio, the device stops reading, so the host's writes
  block. `uwbnetd` also keeps at most one transfer pending in the `cdc_acm`
  driver (checked with `TIOCOUTQ`), so the waiting happens in the host's
  interface queue rather than in USB buffers. The host must therefore
  keep reading while it writes (non-blocking I/O or separate reader and
  writer), or the two ends can wait on each other.
- While there is no link (radio down, or nothing heard from the peer for
  3.5 s) DATA is dropped on arrival, counted as `usb ... dropped (no link)`,
  so the host never stalls on a dead link.
- Device → host DATA is dropped (counted as `usb ... out ... dropped`) when the
  port is closed or the host has not drained the device's ~6 KB USB buffer.

Example: the IPv4 packet `45 00 00 1c ...` is sent as
`COBS(01 45 00 00 1c ...) 00`.

### Useful commands for the daemon

Any console command works (see `help`). The ones a daemon needs:

- `info`: firmware version, own address, peer, link state, MTU.
- `stats`: counters.
- `set <key> <value> ...` then `save`: configuration (see `set` without
  arguments for the keys).

## Over the air

All frames are IEEE 802.15.4 frames using the DW1000's extended (non-standard)
PHR, which allows PSDUs up to 1023 bytes. Both ends must therefore run this
firmware (or another DW1000 in the same mode).

```
data: FC(2) seq(1) dstPAN(2) dst(2) src(2) | dispatch(1) payload(0..1011) | FCS(2)
ack:  FC(2) seq(1)                                                         | FCS(2)
```

- FC `0x8841` (`0x8861` with ACK request): data frame, PAN ID compression,
  16-bit short addresses, frame version 0. Multi-byte fields little-endian.
- Short address: the low 16 bits of the Teensy's factory MAC (OCOTP), unless
  configured. PAN ID default `0x5557`.
- ACKs are generated by the DW1000 in hardware (frame filtering + AUTOACK).

| Dispatch | Meaning | Sent as |
|---|---|---|
| `0x01` IP | one IP packet, handed to the host | unicast to the peer, ACK requested (except UDP with `udparq 0`) |
| `0x02` HELLO | `version_major, version_minor`; peer discovery and link liveness, once a second when nothing else was sent | broadcast, no ACK |
| `0x03` TEST | console ping/flood traffic: `flags(1) id(2) seq(2) sent_us(4) padding`; flag bit 0 = echo requested | unicast, ACK requested |
| `0x04` ECHO | reply to a TEST with the echo flag, same body | unicast, ACK requested |

### Channel access

UWB has no carrier sense, so the firmware uses the DW1000's own receive
status and the 802.15.4 "frame pending" bit:

1. Before transmitting it checks the "preamble / SFD / PHR detected" status
   bits and defers while a frame is arriving.
2. While a node has frames queued, its hardware ACKs carry "frame pending"
   (AACKPEND). A sender that gets such an ACK waits `backoff` µs (default
   800) before its next frame, so the peer can send. Otherwise it continues at
   once.
3. A node that has just received a unicast data frame may transmit at once.
   With traffic in both directions (e.g. TCP data and ACKs) the two ends then
   take turns.
4. With one-way traffic the sender writes its next frame into the chip while
   it waits for the ACK. It writes only as much as finishes before the ACK's
   bytes arrive, because overlapping writes can spoil the ACK.
5. A missing ACK is retried up to `retries` times (default 3) after a random
   backoff of 0..2^n frame-exchange times. A receiver that sees the same
   (source, sequence) twice drops the copy; the hardware has already re-ACKed it.
